# Phase 1 common workspace and operator demo
- Master Admin retains the full working browser demo including multi-company, multi-branch, employee and custom role management. No existing business records or saved roles are migrated, reset or removed.
- MA-003 offers CPQ Operator Template, which prepopulates a custom role editor. Master Admin reviews/saves the role and creates or assigns an active employee in selected active locations. Existing staff roles remain preview-only until granted a complete module.
- The common MA-001 dashboard shows granted modules and scoped quote counts. MA-006A and MA-006 are reused. A combined screen requires all related page and action grants, explicit working-module permission, and all-record visibility in the same assigned branch. Removing a required grant closes the whole module. This includes fictional costs and margins; granular working permissions await backend implementation.
- Product catalog is shared. Configuration/quotation list/lookup, customer choices, branch selection and saves are checked against granted scopes. A reusable configuration requires an assigned internal location for operator saves. No other-scope records are deleted from the backing data.
- Account creation, organization/role management, reset, final review decisions, dispatch and orders remain Master Admin-only. Operators can submit quotations for review and create permitted revisions. Other master maintenance, settings and reports remain Master Admin-only for this increment; operators can choose existing eligible records. Quick-create for restricted masters is disabled.
- No real authentication, secure session, server authorization, tenant isolation, real audit or real transactions. Static code and local storage are inspectable and bypassable; use fictional data only.
- Manual QA: create role and active employee, assign one branch, sign out/in, verify common dashboard and both working modules, create product/configuration/quote, submit review, check denied admin and order routes and cross-scope records, revoke a module grant, return as Master Admin and verify persistence.

## Admin-created employee login (Phase 1)
- Work email is the unique login ID (employee ID also accepted in demo). Only Master Admin creates accounts or resets another employee. Existing invited records read as Pending first login, preserving IDs and assignments. No self-registration.
- New, reset and reactivated accounts receive a non-secret, generated sample code derived from employee ID and version. Admin can display/copy pending credentials; existing active personal passwords are not shown. Existing untouched active seed accounts may autofill public sample credentials for testing. No arbitrary passwords or credential strings are persisted. Legacy sessions require a fresh sign-in.
- First login creates a setup-only demo session. Operational pages redirect to mandatory Change Password until the employee confirms the next generated sample code. Completion activates the account, increments the version, invalidates the old code and opens the assigned workspace or preview. Active employees can change their own sample password. Disabled accounts cannot sign in. Final active Master Admin and self-reset/deactivation actions are protected. Account status/version and setup events persist in existing browser storage.
- Real authentication, user-chosen passwords, secure hashing, random temporary passwords, expiry, rate limiting, automatic lockout, real session revocation, server authorization, secure delivery and tamper-proof logs require production development. Locked is supported as a disabled state, not automatically set in demo.
